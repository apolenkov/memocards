# Grafana Dashboard Guide - Объяснение для Junior

Этот документ объясняет каждую секцию дэшборда Grafana простым языком для junior разработчиков.

## 🎯 Что такое мониторинг?

**Мониторинг** — это система наблюдения за приложением в реальном времени. Представь, что это как панель управления автомобилем, где ты видишь скорость, уровень топлива, температуру двигателя и т.д.

**Grafana** — это система визуализации метрик, которая показывает красивые графики и дашборды.

## 📊 Архитектура мониторинга

```
Приложение (memocards-app)
    ↓ metrics
Spring Boot Actuator (/actuator/prometheus)
    ↓ scrape
Prometheus (собирает и хранит метрики)
    ↓ query
Grafana (показывает графики и дашборды)
```

## 🔍 Основные методологии мониторинга

### RED Method (для HTTP-сервисов)
- **Rate** — количество запросов в секунду
- **Errors** — процент ошибок
- **Duration** — время ответа

### USE Method (для ресурсов)
- **Utilization** — загрузка ресурса (%)
- **Saturation** — очередь/насыщение
- **Errors** — ошибки использования ресурса

## 🚦 Секция 1: Application Status (Статус приложения)

### Панели:

#### 1.1 Application Status (Gauge)
```
Метрика: up{application="memocards"}
Описание: Работает ли приложение
Цвета: 🟢 Зеленый = работает, 🔴 Красный = не работает
```

**Что это значит?**
- Если значение `1`, приложение доступно
- Если значение `0`, приложение упало или недоступно

**Когда смотреть?**
- Первое, что проверяешь при проблемах
- При деплое новой версии

---

#### 1.2 Application Uptime (Stat)
```
Метрика: process_uptime_seconds
Описание: Сколько времени приложение работает без перезагрузки
Формат: дни:часы:минуты:секунды
```

**Что это значит?**
- Показывает время с последнего старта приложения
- Если значение маленькое, приложение недавно перезагружалось

**Когда смотреть?**
- После деплоя — проверить, что приложение стартовало
- При неожиданных перезагрузках

## 🔴 Секция 2: RED Method - HTTP Metrics

### 2.1 HTTP Request Rate (Requests/sec)

```
Метрика: sum(rate(http_server_requests_seconds_count[1m])) by (method, uri)
Описание: Сколько HTTP запросов в секунду приходит
Группировка: по HTTP методу (GET, POST) и URI
```

**Что это значит?**
- **Rate** — количество запросов в секунду
- График показывает нагрузку на приложение
- `method` — GET, POST, PUT, DELETE
- `uri` — путь запроса (например, `/decks`, `/users`)

**Когда смотреть?**
- При росте нагрузки на сервер
- Для понимания, какие эндпоинты самые популярные
- Для выявления аномального трафика (DDoS, ошибки клиентов)

**Пример чтения:**
```
GET /decks → 150 req/s (150 запросов в секунду)
POST /users → 20 req/s (20 запросов в секунду)
```

---

### 2.2 HTTP Error Rate (% Failed Requests)

```
Метрика: (sum(rate(http_server_requests_seconds_count{status=~"5.."}[1m])) / 
          sum(rate(http_server_requests_seconds_count[1m]))) * 100
Описание: Процент ошибок от всех запросов
Thresholds: 🟢 0-1% OK, 🟡 1-5% Warning, 🔴 >5% Critical
```

**Что это значит?**
- **Errors** — процент 5xx ответов от всех запросов
- `status=~"5.."` — все статусы начинающиеся с 5 (500, 502, 503, etc)

**Когда смотреть?**
- Постоянно! Это ключевой индикатор проблем
- При росте > 1% — начать расследование
- При росте > 5% — критическая ситуация

**Пример чтения:**
```
0.5% — отлично, приложение стабильно
2.5% — проблема! Начать debug
8.0% — критично! Срочно исправлять
```

---

### 2.3 HTTP Response Time (Avg/P50/P95/P99/Max)

```
Метрики:
- Avg: среднее время ответа
- P50 (median): 50% запросов быстрее
- P95: 95% запросов быстрее
- P99: 99% запросов быстрее
- Max: самый медленный запрос
Единица: миллисекунды (ms)
SLO Target: P95 ≤ 400ms
```

**Что это значит?**
- **Duration** — как долго приложение отвечает на запросы
- **Percentiles (процентили)** — разные уровни производительности

**Процентили простыми словами:**
```
100 запросов:

P50 (median): 50-й по скорости = 100ms
→ 50 запросов быстрее 100ms, 50 медленнее

P95: 95-й по скорости = 500ms
→ 95 запросов быстрее 500ms, только 5 медленнее

P99: 99-й по скорости = 1000ms
→ Только 1 запрос из 100 медленнее 1000ms
```

**Когда смотреть?**
- Всегда! Это главный индикатор производительности
- P95 > 400ms — начать оптимизацию
- P99 очень высокий — искать медленные запросы

**Пример чтения:**
```
Avg: 50ms   — средний запрос быстрый
P50: 45ms   — половина запросов < 45ms
P95: 380ms  — 95% запросов < 380ms ✅
P99: 1200ms — 1% запросов > 1 сек ⚠️
Max: 5000ms — есть очень медленные запросы ❌
```

**Action items:**
- P95 > SLO → оптимизировать код/базу данных
- P99 >> P95 → есть выбросы (outliers), найти их в логах
- Max очень высокий → конкретный эндпоинт тормозит

## 🎯 Секция 3: SLO Compliance (Соответствие целям качества сервиса)

### Что такое SLO?

**SLO (Service Level Objective)** — это цели качества работы сервиса, которые мы обещаем пользователям.

**Пример:** "99.9% запросов ответят за < 400ms"

### 3.1 Latency SLO (/decks) - P95 ≤ 400ms

```
Метрика: histogram_quantile(0.95, sum(rate(http_server_requests_seconds_bucket{uri="/decks"}[1m])) by (le)) * 1000
SLO: P95 latency ≤ 400ms
Thresholds: 🟢 ≤ 400ms, 🟡 400-500ms, 🔴 > 500ms
```

**Что это значит?**
- Проверяем только эндпоинт `/decks`
- 95% запросов должны быть < 400ms

**Когда смотреть?**
- Постоянно мониторим соответствие SLO
- При деградации ниже 400ms — расследование

---

### 3.2 Error Rate SLO - 5xx ≤ 0.5%

```
Метрика: (sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m])) / 
          sum(rate(http_server_requests_seconds_count[5m]))) * 100
SLO: Error rate ≤ 0.5%
Thresholds: 🟢 ≤ 0.5%, 🟡 0.5-1%, 🔴 > 1%
```

**Что это значит?**
- Только 0.5% запросов могут быть ошибочными
- При превышении — серьезная проблема

---

### 3.3 Database SLO - P95 Query ≤ 50ms

```
Метрика: histogram_quantile(0.95, sum(rate(hikaricp_connections_usage_seconds_bucket[1m])) by (le)) * 1000
SLO: P95 database query ≤ 50ms
Thresholds: 🟢 ≤ 50ms, 🟡 50-100ms, 🔴 > 100ms
```

**Что это значит?**
- Время выполнения SQL запросов
- 95% запросов к базе должны быть < 50ms

**Когда смотреть?**
- При медленных SQL запросах
- Для оптимизации базы данных

---

### 3.4 Availability SLO - Uptime ≥ 99.9%

```
Метрика: avg(up{application="memocards"}) * 100
SLO: Availability ≥ 99.9%
Thresholds: 🟢 ≥ 99.9%, 🟡 99-99.9%, 🔴 < 99%
```

**Что это значит?**
- Приложение должно работать 99.9% времени
- За месяц это ≈ 43 минуты downtime

## 🗄️ Секция 4: USE Method - Resource Metrics

### 4.1 HikariCP Pool Usage

```
Метрика: (hikaricp_connections_active / hikaricp_connections_max) * 100
Описание: Использование пула подключений к БД
Thresholds: 🟢 0-70%, 🟡 70-90%, 🔴 > 90%
```

**Что это значит?**
- **HikariCP** — пул подключений к PostgreSQL
- Сколько процентов соединений занято

**Почему важно?**
- Если пул заполнен на 100%, новые запросы ждут
- Длительное ожидание = медленные ответы

**Action items:**
- > 70% — подумать об увеличении `max-pool-size`
- > 90% — критично! Проверить утечки подключений

---

### 4.2 HikariCP Connections

```
Метрики:
- Active: занятые соединения
- Idle: свободные соединения
- Max: максимальный размер пула
- Pending: запросы в очереди
```

**Что это значит?**
- **Active** — соединения, которые выполняют запросы
- **Idle** — свободные соединения в пуле
- **Pending** — запросы ждут свободное соединение (плохо!)

**Красные флаги:**
- `Pending > 0` — пул истощен
- `Active ≈ Max` — нужно увеличить размер пула

---

### 4.3 JVM Heap Usage

```
Метрика: (sum(jvm_memory_used_bytes{area="heap"}) / 
          sum(jvm_memory_max_bytes{area="heap"})) * 100
Описание: Использование памяти кучи (heap)
Thresholds: 🟢 0-70%, 🟡 70-80%, 🔴 > 80%
```

**Что это значит?**
- **Heap (куча)** — основная память приложения
- JVM выделяет память из heap для объектов

**Почему важно?**
- > 80% — риск OutOfMemoryError
- GC (garbage collector) начинает работать чаще → тормоза

**Action items:**
- > 80% — проверить утечки памяти
- Очень быстро растет — memory leak

---

## 💾 Секция 5: SQL/Database Metrics

### 5.1 SQL Query Execution Time

```
Метрики:
- Avg SQL Query Time: среднее время
- Max SQL Query Time: максимум
Targets: avg < 50ms, max < 100ms
```

**Что это значит?**
- Сколько времени выполняются SQL запросы
- Высокие значения → медленная БД или плохие индексы

**Action items:**
- Avg > 50ms — проверить индексы
- Max > 100ms — найти и оптимизировать конкретный запрос

---

### 5.2 SQL Query Rate

```
Метрика: sum(rate(hikaricp_connections_usage_seconds_count[1m]))
Описание: Количество SQL запросов в секунду
```

**Что это значит?**
- Нагрузка на базу данных
- Высокий rate → проверить на N+1 queries

---

### 5.3 Connection Acquisition Time

```
Метрика: sum(rate(hikaricp_connections_acquire_seconds_sum[1m])) / 
          sum(rate(hikaricp_connections_acquire_seconds_count[1m])) * 1000
Описание: Время получения соединения из пула
```

**Что это значит?**
- Сколько времени запрос ждет свободное соединение
- Высокое значение → пул перегружен

**Красные флаги:**
- > 10ms — пул заполнен
- Нужно увеличить `hikaricp.maximum-pool-size`

---

### 5.4 Connection Timeouts (5m)

```
Метрика: increase(hikaricp_connections_timeout_total[5m])
Описание: Количество таймаутов за 5 минут
Thresholds: 🟢 0, 🔴 > 0
```

**Что это значит?**
- **Timeout** — запрос не дождался свободного соединения
- Критично! Приложение не может работать с БД

**Action items:**
- > 0 — срочно увеличить пул
- Проверить на утечки соединений (не закрытые транзакции)

---

## ☕ Секция 6: JVM Metrics

### 6.1 JVM Heap Memory

```
Метрики:
- Heap Used: использовано
- Heap Max: максимум
- Heap Committed: зарезервировано JVM
```

**Что это значит?**
- Динамика использования памяти
- Если `Used ≈ Max` — риск OOM

---

### 6.2 JVM Threads

```
Метрики:
- Live Threads: активные потоки
- Peak Threads: максимальное количество
- Daemon Threads: фоновые потоки
```

**Что это значит?**
- **Thread** — поток выполнения кода
- Java приложение использует многопоточность
- Слишком много потоков → context switching → тормоза

**Action items:**
- Резкий рост threads — проверить на deadlocks
- Очень высокий peak — возможно thread leak

---

### 6.3 GC Pause Time

```
Метрика: sum(rate(jvm_gc_pause_seconds_sum[1m]))
Описание: Время сборки мусора
```

**Что это значит?**
- **GC (Garbage Collector)** — очистка неиспользуемой памяти
- Во время GC приложение "замораживается"

**Почему важно?**
- Высокий GC time → частые паузы → медленные ответы
- Указывает на проблемы с памятью

## 💰 Секция 7: Cache Metrics

### 7.1 Cache Hit Rate (Spring Cache)

```
Метрика: (sum(rate(cache_gets_total{result="hit"}[5m])) / 
          sum(rate(cache_gets_total[5m]))) * 100
Описание: Процент попаданий в кэш
Target: > 90%
```

**Что это значит?**
- **Hit** — значение найдено в кэше
- **Miss** — значение не найдено, загружено из БД
- Высокий hit rate → меньше нагрузка на БД

**Когда смотреть?**
- < 80% — кэш неэффективен
- Проверить TTL и размер кэша

---

### 7.2 Cache Operations Rate (Spring Cache)

```
Метрики:
- Gets (hit): попадания
- Gets (miss): промахи
- Puts: добавления в кэш
- Evictions: удаления из кэша (LRU)
```

**Что это значит?**
- Динамика работы кэша
- Evictions → кэш переполнен, элементы вытесняются

---

### 7.3 Cache Size

```
Метрика: cache_size
Описание: Текущий размер кэша
```

**Что это значит?**
- Количество элементов в кэше
- Сравнить с `maxSize` настройкой

---

### 7.4 Cache Hit Rate (Custom - pagination-count)

```
Метрика: (sum(rate(cache_access_total{result="hit"}[5m])) / 
          sum(rate(cache_access_total[5m]))) * 100
Описание: Hit rate для кастомного кэша
Target: > 80%
```

**Для junior:**
- Это кастомный кэш для подсчета страниц пагинации
- Session-scoped (разный для каждой вкладки браузера)

---

## 📦 Секция 8: Container Metrics (cAdvisor)

### 8.1 Container CPU Usage

```
Метрика: rate(container_cpu_usage_seconds_total{name=~"memocards-app.*"}[1m]) * 100
Описание: CPU использование контейнера
Target: < 70%
```

**Что это значит?**
- Процент загрузки процессора контейнером
- > 90% — приложение не справляется с нагрузкой

---

### 8.2 Container Memory Usage

```
Метрика: (container_memory_usage_bytes{name=~"memocards-app.*"} / 
          container_spec_memory_limit_bytes{name=~"memocards-app.*"}) * 100
Описание: Использование памяти контейнера
Target: < 80%
```

**Что это значит?**
- Процент использования памяти контейнером
- > 90% — риск OOMKilled (Docker убьет контейнер)

---

### 8.3 Container Network I/O

```
Метрики:
- Rx: получено байт/сек
- Tx: отправлено байт/сек
```

**Что это значит?**
- Сетевая активность контейнера
- Помогает понять объем трафика

## 🖥️ Секция 9: OS Metrics (Node Exporter)

### 9.1 CPU Usage

```
Метрика: 100 - (avg(irate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
Описание: Общая загрузка CPU хоста
Target: < 70%
```

**Что это значит?**
- Загрузка процессора всей системы (не только контейнера)
- > 90% — не хватает CPU для всей системы

---

### 9.2 Memory Usage

```
Метрика: (1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)) * 100
Описание: Использование памяти хоста
Target: < 80%
```

**Что это значит?**
- Память всей системы (все контейнеры + ОС)
- > 90% — система может использовать swap → тормоза

---

### 9.3 Disk Usage

```
Метрика: (1 - (node_filesystem_avail_bytes{mountpoint="/"} / 
                node_filesystem_size_bytes{mountpoint="/"})) * 100
Описание: Заполненность диска
Target: < 85%
```

**Что это значит?**
- Сколько места осталось на диске
- > 95% — критично! Приложение может упасть

---

### 9.4 Network I/O

```
Метрики:
- Rx: получено байт/сек
- Tx: отправлено байт/сек
```

**Что это значит?**
- Сетевая активность всего сервера
- Помогает понять общий трафик

---

### 9.5 Disk I/O (IOPS)

```
Метрики:
- Reads: операций чтения/сек
- Writes: операций записи/сек
```

**Что это значит?**
- Нагрузка на диск
- Высокая нагрузка → медленные запросы к БД

---

### 9.6 Load Average

```
Метрики:
- 1min: средняя нагрузка за 1 минуту
- 5min: средняя нагрузка за 5 минут
- 15min: средняя нагрузка за 15 минут
Target: < количество CPU ядер
```

**Что это значит?**
- Среднее количество процессов в очереди
- Load > CPU cores → система перегружена

**Пример:**
```
4 CPU cores, Load = 6.0 → система перегружена
4 CPU cores, Load = 2.0 → норма
```

## 🚨 Как использовать этот дэшборд?

### Ежедневный мониторинг (чтобы быть спокойным):

1. **Application Status** = 🟢 Up
2. **Error Rate** < 1%
3. **Response Time P95** < 400ms
4. **No Connection Timeouts**

### При проблемах (Debug workflow):

1. **Посмотреть ERROR Logs** — что упало?
2. **Error Rate** — сколько ошибок?
3. **Response Time** — где тормозит?
4. **Database Metrics** — медленные запросы?
5. **JVM Heap** — утечка памяти?
6. **Container Metrics** — не хватает ресурсов?

### Чеклист при деплое:

1. ✅ Application Status = Up
2. ✅ No ERROR logs
3. ✅ Error Rate = 0%
4. ✅ Response Time нормальный
5. ✅ Нет Connection Timeouts

## 🤔 Частые вопросы для junior

### Q: Что такое PromQL?
**A:** Язык запросов Prometheus для получения метрик. Пример: `rate(http_server_requests_seconds_count[1m])`

### Q: Чем отличается Rate от Error Rate?
**A:** 
- **Rate** — сколько запросов в секунду (объем)
- **Error Rate** — сколько процентов запросов ошибочных (качество)

### Q: Что такое P95?
**A:** 95-й процентиль — 95% запросов быстрее этого значения. Используется для SLO.

### Q: Почему метрики обновляются не мгновенно?
**A:** Prometheus собирает метрики каждые 15 секунд. Grafana обновляет дэшборд каждые 30 секунд.

### Q: Как найти конкретный медленный запрос?
**A:** В Response Time смотреть legend по URI. Затем посмотреть лogs для этого эндпоинта.

### Q: Что делать если Connection Pool на 90%?
**A:** Увеличить `hikaricp.maximum-pool-size` в `application.yml`. Или найти утечку соединений.

### Q: Память растет постоянно — это нормально?
**A:** Нет! Это memory leak. Проверить код на не закрытые ресурсы, цикличные ссылки.

Мониторинг — это твоя система раннего предупреждения. Правильное использование метрик помогает находить проблемы до того, как они станут критичными.

**Главное правило:** Не паниковать при небольших отклонениях, но реагировать быстро на критические пороги!
